# 测试驱动开发

## 核心理念

**核心原则**：测试应该通过公共接口验证行为，而非实现细节。代码可以完全改变，但测试不应该随之改变。

**好的测试**是集成式的：它们通过公共 API 走真实的代码路径。它们描述系统做了_什么_，而不是_怎么_做的。好的测试读起来就像规格说明——"用户可以用有效购物车结账"准确告诉你存在什么能力。这些测试能在重构中存活，因为它们不关心内部结构。

**坏的测试**与实现耦合。它们模拟内部协作者、测试私有方法，或通过外部手段验证（比如直接查询数据库而不是使用接口）。危险信号：你重构时测试挂了，但行为并没有改变。如果你重命名了一个内部函数而测试失败了，那些测试测的是实现，不是行为。

参见 [tests.md](tests.md) 了解示例，[mocking.md](mocking.md) 了解模拟指南。

## 反模式：水平切片

**不要先写完所有测试，再写所有实现。** 这是"水平切片"——把 RED 当成"写所有测试"，把 GREEN 当成"写所有代码"。

这会产生**糟糕的测试**：

- 批量编写的测试测的是_想象中_的行为，而非_实际的_行为
- 你最终测的是事物的_形状_（数据结构、函数签名），而不是面向用户的行为
- 测试对真正的变化失去敏感——行为坏了测试通过，行为正常测试反倒失败
- 你跑到了车灯前面，在理解实现之前就锁定了测试结构

**正确做法**：通过示踪弹进行垂直切片。一个测试 → 一个实现 → 重复。每个测试都基于上一个周期中学到的经验。因为你刚写完代码，你确切知道什么行为重要以及如何验证它。

```
错误（水平）：
  RED:   测试1, 测试2, 测试3, 测试4, 测试5
  GREEN: 实现1, 实现2, 实现3, 实现4, 实现5

正确（垂直）：
  RED→GREEN: 测试1→实现1
  RED→GREEN: 测试2→实现2
  RED→GREEN: 测试3→实现3
  ...
```

## 工作流

### 1. 规划

在编写任何代码之前：

- [ ] 与用户确认需要哪些接口变更
- [ ] 与用户确认要测试哪些行为（按优先级排序）
- [ ] 识别[深模块](deep-modules.md)的机会（小接口，深实现）
- [ ] 为[可测试性](interface-design.md)设计接口
- [ ] 列出要测试的行为（而非实现步骤）
- [ ] 获得用户对计划的批准

提问："公共接口应该是什么样的？哪些行为最重要需要测试？"

**你不可能测试所有东西。** 与用户确认哪些行为最重要。将测试精力集中在关键路径和复杂逻辑上，而非每一个可能的边界情况。

### 2. 示踪弹

写一个只确认一件事的测试：

```
RED:   为第一个行为写测试 → 测试失败
GREEN: 写最少代码使其通过 → 测试通过
```

这就是你的示踪弹——证明端到端路径是通的。

### 3. 增量循环

对每个剩余行为：

```
RED:   写下一个测试 → 失败
GREEN: 写最少代码使其通过 → 通过
```

规则：

- 每次只写一个测试
- 只写足以通过当前测试的代码
- 不要预先为未来的测试写代码
- 让测试聚焦于可观察的行为

### 4. 重构

所有测试通过后，寻找[重构候选项](refactoring.md)：

- [ ] 提取重复代码
- [ ] 加深模块（将复杂性隐藏到简单接口之后）
- [ ] 在自然的地方应用 SOLID 原则
- [ ] 思考新代码揭示的已有代码问题
- [ ] 每次重构步骤后运行测试

**永远不要在 RED 状态下重构。** 先回到 GREEN。

## 每轮检查清单

```
[ ] 测试描述的是行为，而非实现
[ ] 测试仅使用公共接口
[ ] 测试能在内部重构后存活
[ ] 代码对当前测试是最少的
[ ] 没有添加推测性的功能
```
